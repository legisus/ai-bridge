# Chrome in Docker on the Mac — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans. Steps use checkbox syntax.

**Goal:** Build the container from `docs/superpowers/specs/2026-11-26-docker-chrome-design.md`: one Google Chrome (no Chromium anywhere in the image) with the AI Browser Bridge extension and the relay inside a Colima container on this Mac, driven by the unchanged Mac-side CLI through a published loopback port. The co-host bot stays on the Mac and reaches Turo through it once its `transport` is flipped.

**Spec:** the design above, approved by the operator on 2026-11-27 with: "bot stays on this mac, using chrome in docker. no chromium."

**Out of scope for this build:** the one-time switch-over (stopping the host relay, removing the Mac extension, flipping the bot's `transport`, the operator's logins). It needs the operator's logins and a quiet window; this build ships a runbook for it (`docs/DOCKER-CHROME.md`) and leaves the live host layout untouched.

**Architecture:** `deploy/docker-chrome/` holds the image (Selkies base without a browser + Google Chrome `.deb` + Node 22 + the repo's `server/` and `extension/`), an s6 service for the relay, `chrome-start.sh` (the Wayland session's autostart: a loop that starts Chrome and runs `provision.py` after every start) and `compose.yml`. `bin/bridge-docker` is the Mac-side helper. Everything the container publishes or mounts is a variable with the production value as default, so the same compose file runs a throwaway smoke project and a staging instance on another port next to the live host relay.

## Builder decisions (the design's open questions and what the build added)

| # | Question | Decision | Why |
|---|---|---|---|
| D1 | Keep the base image's Chromium or remove it | **Neither: use a base that never had it.** `ghcr.io/linuxserver/baseimage-selkies:debiantrixie` pinned by digest (`sha256:793fc362…`, ls153, the parent of `linuxserver/chromium`). | Operator requirement "no chromium". The parent image carries Selkies, labwc, s6 and the `/config` layout the spike ran on; `linuxserver/chromium` only adds the Chromium packages and a wrapper on top. The smoke test proves no chromium package or binary exists and that the running browser is Google Chrome. |
| D2 | Extension in the image or bind-mounted from the clone | **Copied into the image** (`/opt/ai-bridge/extension`), and `extension` is taken off the repo's `.dockerignore` (this Mac's Docker has no BuildKit, so a per-Dockerfile ignore file would not be honoured; the other image copies `server/` only, a larger build context changes nothing for it). | Relay and extension always come from the same commit; a half-finished edit in the working tree can never reach the container's browser at the next Chrome start; the container does not depend on which branch the clone is on. Update = `bridge-docker build && bridge-docker up`. The image label records the git commit and the Chrome version. |
| D3 | Selkies password on or off | **Off by default**; `CUSTOM_USER` / `PASSWORD` are passed through from the environment when set. | The screen port is published on the Mac's loopback only. |

Nothing on the Mac is torn down. | Still unanswered. |
| D6 | (added) How to run next to the live host relay | Compose variables: `BRIDGE_PUBLISH_PORT` (8765), `SCREEN_PUBLISH_PORT` (3000), `BRIDGE_DATA_DIR` (`~/.ai-browser-bridge`), `CHROME_CONFIG_DIR` (`~/docker/ai-bridge-chrome/config`), `CHROME_DOWNLOADS_DIR` (`~/Downloads`). `bridge-docker --staging` = port 8766, its own data dir and downloads dir under `~/docker/ai-bridge-chrome/`, **the production profile volume** (so logins done in staging are the production logins). `bridge-docker up` refuses when the publish port is already held by another process, and refuses the production data dir while a host relay is alive. | The host relay and a container relay must never share `tabs.json`/`bridge.log`; staging lets the operator log in before the switch-over. |
| D7 | Incognito addition | **Kept.** `newTab {"incognito":true}` opens an incognito window; refused with a clear error when the extension is not allowed in incognito (Chrome would otherwise open a window the extension cannot see or close). `listTabs` rows carry `"incognito": true`. | Design section "Bridge addition"; the guard is the builder's addition. |
| D8 | How `provision.py` writes `chrome.storage.local` | From the extension's own `options.html` opened as a CDP target (fallback: the service-worker target, as in the spike). | A page target exists as soon as it is created; a service-worker target is only listed while the worker is awake. |
| D9 | Relay process | s6 `longrun` service `svc-relay` running as `abc`. | Restarts by itself; independent of the Wayland session. |
| D10 | Chrome version | Whatever `google-chrome-stable_current_arm64.deb` is at build time; build arg `CHROME_DEB_URL` pins another. The version is written to `/opt/ai-bridge/CHROME_VERSION` and an image label. | Design. Chrome is updated by rebuilding, never inside the running container. |
| D11 | Colima size and start at login | **Done by the builder:** `colima stop` → `colima start --cpu 4 --memory 6` (persisted in `~/.colima/default/colima.yaml`), then Colima handed to `brew services` so it starts at login. `mem_limit` from `CHROME_MEM_LIMIT`, default 3g. | Nothing live runs in Docker (the spike container is stopped), so restarting the VM disturbs nothing. ## Plan review, round 1 (Astra, 2026-11-27: DO NOT PROCEED) — what changed

| # | Finding | Change |
|---|---|---|
| 1 | Building in the live checkouts is not isolation | **Both repositories are built in separate git worktrees** (`~/IdeaProjects/ai-bridge-docker-chrome` on `docker-chrome`; `~/IdeaProjects/turo-cohost-assistant-docker-chrome` on the bot branch). The live ai-bridge checkout is back on `fix/intent-gate-expiry`, clean (the bridge log shows no extension reconnect while the first edits were in it). The image is built from the worktree; the one-off bot probe runs from the bot worktree with `AI_BRIDGE_CLI` pointing at the ai-bridge worktree. Nothing reaches the live folders before the PRs are merged. |
| 2 | Staging and production can open one profile at once | `bridge-docker up` refuses when **any** other container (running or stopped) mounts the profile directory; `chrome-start.sh` holds a lock, waits for a running Chrome to exit and only then removes `Singleton*`; the runbook stops staging before production starts. Smoke asserts the refusal. |
| 3 | Incognito tests miss the interleavings | The permission query sits **after** the pending entry and the access re-check, before the dispatch (validate → pending → re-check → query → dispatch → complete). Tests: revoke during the query, revoke during creation (late tab closed), late tab that cannot be closed stays owned, query rejects, creation fails, reload while a creation is pending, privileged/disallowed destinations, redaction. |
| 4 | Window-tab fallback can lose or misassign ownership | Incognito: ownership only of the single incognito tab Chrome returns for the window it created; anything else is "unidentified" — no ownership, nothing closed, pending released, event logged, the error names the window. The old `newWindow` path no longer dereferences a missing tab outside the cleanup path. Stub and tests cover no tab / a foreign tab / two tabs. |
| 5 | A new incognito window is not a fresh session | Bot task 13 rewritten: one second-account run at a time (file lock); an incognito tab that is already open is a stop, not a reuse (agent-owned leftovers are closed first, anything else is reported); the logged-in account is verified before data is read; closing is verified through `listTabs` and a failure is reported, not swallowed. |
| 6 | Regular vs incognito window for ordinary tabs | Defined in the extension: with incognito access on, an ordinary `newTab` names a regular window (or opens one when only incognito windows exist) and `newWindow` asks for `incognito:false`; `incognito` + `windowId` is refused; the result carries `incognito:true` whenever the tab really is incognito. With incognito access off (the Mac today) the code path and result shapes are unchanged — tested. Manifest stays "spanning"; a test pins it. |
| 7 | `/data` initialisation | `bridge-docker up` creates and validates the three mounts (owner, writable, an existing token readable and kept); the relay service checks `/data` as the image user before starting and says what is wrong; service contract `AI_BRIDGE_HOME=/data BRIDGE_BIND=0.0.0.0 BRIDGE_PORT=8765`, ordered after `init-services`. Smoke asserts the relay uid, directory/token modes on the Mac and the token surviving a container restart. |
| 8 | Chrome loop without an exit before CDP | CDP wait bounded by 60 s and by the launched process; a Chrome that never opens the port is stopped and restarted; the Wayland socket is awaited; TERM/INT/HUP stop Chrome cleanly. |
| 9 | Provisioning idempotence | An already loaded and enabled extension is **not** loaded again (that would be a reload and lose tab ownership); one provisioning at a time (file lock); an executable extension context is awaited; throwaway tabs are closed in `finally`. Unit tests + smoke: a run by hand keeps `extGen`, `serverId` and an owned tab. Added step 0: Developer mode on (found on the first run: without it Chrome disables the unpacked extension as soon as "Allow in incognito" reloads it). |
| 10 | Restart checks prove too little | After a Chrome restart and after a container restart the smoke repeats stealth `eval`, incognito open/eval/list/close and the cleanup; Chrome restart = same `serverId`, higher `extGen`; container restart = new `serverId`, same token, profile data still there. |
| 11 | Browser, sandbox, screen under-proved | Smoke: package is Google's `google-chrome-stable`, running executable is `/opt/google/chrome/chrome`, no other browser executable anywhere in the filesystem (the build fails on one too), `chrome://sandbox` over container-local CDP says "adequately sandboxed", 9222 listens on the container's loopback only and is unpublished, the screen port serves the Selkies page. |
| 12 | Host-preservation and teardown | Smoke records the host relay's `serverId/extGen/accessGen/session` and listening pid before and after and fails on any difference; every CLI call names its port and state directory; project and directories are unique per run; teardown is verified before `SMOKE OK`. |
| 13 | Bot probe before the bot changes | Task 8b's bot probe moved after tasks 11–15: an inbox-only read through `turo_chrome.py list` from the bot worktree; the daemon and `ensure_chrome()` are not started. |
| 14 | Runbook ordering | `docs/DOCKER-CHROME.md` orders the switch-over: quiet window → staging down → host relay, launchd job and native host off → Mac extension off (or moved to another port, the operator's call) → production up and verified → bot transport → smoke. Rollback releases the container's ports first and restores the native-host registration. All of it is the operator's to run. |
| 15 | D4/D11 as unconditional steps | D4 is done (both copies exist; never overwritten). D11 is done (4 CPU / 6 GB, `brew services`). Disk: the VM's Docker disk is 20 GB with 6 GB free after the build; the runbook gives the non-destructive remedy (`colima stop && colima start --disk 40`; Colima only grows a disk) and the spike images as what the operator may delete. |
| 16 | Build provenance | Full base digest in the Dockerfile; the image label carries the commit, `-dirty` when the copied sources differ from it; the installed Chrome version and the `.deb`'s sha256 are recorded in the image and printed by the build; `CHROME_DEB_URL` + `CHROME_DEB_SHA256` pin a package. |

## Plan review, round 2 (Astra, 2026-11-27: DO NOT PROCEED, 4 resolved / 12 partly) — what changed

| # | Left open in round 2 | Change |
|---|---|---|
| 2 | Profile exclusivity: path aliases, concurrent starts, a lock that is only container-local | `bridge-docker` compares physical paths; `up` is serialized on the Mac (atomic lock directory); the Chrome loop's lock file moved onto the profile volume (`/config/.chrome-profile.lock`), so it holds across containers and automatic restarts. Smoke: three spellings of the path, two concurrent `up`s, a second container started around the helper. |
| 3 | Expiry (not revoke) during the permission query and during creation | Two deterministic tests with a timed grant whose deadline passes inside the query / inside `windows.create`. |
| 4 | The ordinary `newWindow` path still guessed with `tabs.query` | One helper for every window the command creates: ownership only of the single tab Chrome reports, of the expected kind; otherwise unidentified (no ownership, nothing closed, event, error). Tests: no tab, two tabs, a foreign tab present, an incognito tab in a regular window. |
| 6 | A failed permission query fell back to "current window"; `newWindow` + `windowId` undefined | Unknown is treated as "may see incognito": the regular window is named from the window list, or a regular window is opened; `incognito`/`newWindow` together with `windowId` is refused. |
| 7 | Existing state directory / token modes not validated; PUID vs invoking user; recreation | Mode 700 / token 600 / ownership are required (refused, not repaired); PUID/PGID must be the invoking user's; smoke recreates the container (`down` + `up`) and checks token and profile data. |
| 8 | Unbounded `curl`, TERM + endless `wait`, provisioning child | `curl -m 2`; stop = ask (10 s) → TERM (5 s) → KILL; a provisioning run is capped at 180 s and its child is terminated with it. Smoke runs the loop against a stand-in browser that never opens the debug port. |
| 9 | A tab leaked when attach failed or the transport broke while waiting | Target acquisition is exception-safe; two unit tests reproduce both leaks. |
| 10 | Fresh `browserSession`, no carried-over ownership | Smoke leaves an owned tab open across a Chrome restart and asserts a new `browserSession`, an empty `agentTabs`, and a registry with no current tab (the old one is dead or already pruned). |
| 11 | Screen: connection + input | **Not done.** The smoke checks that the screen page is served; a pixel-and-input check of the vendor's screen stack is not something this job does. Documented as a by-eye check (`bridge-docker screen`). |
| 12 | Teardown before compare; scratch deleted while a container lives; other host identities | Scratch directories are removed only when no container of the run is left; host comparison happens after teardown; both ports are checked; the Mac Chrome's pid and the pids of `HOST_WATCH_LABELS` launchd jobs are compared. |
| 14 | Rollback of Variant B (Manual mode) | The guide's rollback restores native provisioning (Manual mode off or the original token), stops the second relay, and keeps the jobs paused until `bridge ping` is green. |
| 16 | Image identity | `bridge-docker build` labels the image with the installed Chrome version and package checksum; the smoke prints the image id and source commit and is run on an image built from a clean commit. |
| new | State-directory guard bypass by alias; early return for an existing project | Canonical paths; the state and profile checks run on every `up`; another container on the same state directory is refused. |
| new | A committed `.pyc` | Removed; `__pycache__` ignored (git and Docker); the test does not write bytecode. |
